# データ設計

各テーブルの主キーは文字列 ID。作成・更新日時は ISO 8601、利用者が選ぶ実施日はローカル日付の YYYY-MM-DD。初期データや単一設定には固定 ID、追加データには UUID を使う。

| 型 | 保存内容 |
| --- | --- |
| UserProfile | 基本情報、目的、優先部位、トレーニング方針 |
| TrainingGoal | BIG3 の合計目標と種目別目標 |
| Exercise | 種目名、主な部位 |
| Gym | ジム名 |
| GymEquipment | ジム ID、設備名、利用可能フラグ |
| WorkoutTemplate | A/B/C、名称、種目・セット数・回数の計画 |
| WorkoutSession | 実施日、メニュー名、ローテーション、ジム、状態、種目の順番とメモ |
| WorkoutSet | セッション・セッション内種目 ID、保存順、重量、回数、強度、セット種別、完了状態 |
| ReadinessCheck | 日付、利用時間、ジム、睡眠、疲労、筋肉痛、違和感、要望 |
| PersonalRecord | 種目 ID と登録自己ベスト重量 |
| CoachingRecommendation | コーチ提案のメニュー名と計画 |
| AppSettings | 休憩時間 |
| DailyCondition | 日付、睡眠時間と質、疲労・ストレス・意欲、部位別筋肉痛、痛み、任意の体重、運動予定、自由記述 |
| SavedMenu | 登録日、ジムID、出所（端末／AI）、バージョン付きの詳細提案 |
| CoachReply | 相談日、モード（レビュー／中長期分析）、回答テキスト |

メニューからセッション作成時に計画を展開する。後からメニューを編集しても保存した実績は変化しない。登録自己ベストと完了本セットの実測 1 回重量の最大値を自己ベストとして表示する。推定1RMは完了本セットの1回重量または2〜10回に Epley 式を適用した最大値。総負荷量は完了本セットの重量×回数の合計。

バックアップは版番号と全テーブルの行を持つ。復元前に必須フィールド、キーの一意性、関連レコードの存在を確認し、トランザクションで置き換える。

Dexie バージョン2は `conditions`、`coachMenus`、`coachReplies` を追加する。既存テーブルと旧 `readiness` 行は引き継ぐ。旧行には5段階入力がないため、日次スコアの入力として使わない。種目の必須設備とセッション内種目の休憩秒数は後方互換の任意フィールド。日次コンディションは日付が一意で、同日の再保存は既存のIDと作成日時を使う。

バックアップ版2に新規3テーブルを含める。版1の復元時は3テーブルを空として扱う。保存済み提案はA/B/Cの基本メニューとは別に管理し、実行時に新しいセッション下書きを作る。

第3段階でもIndexedDBのスキーマは版2、バックアップも版2を継続する。公開向けのサンプル初期値が作成されるのは、端末・ブラウザーの保存領域に初期設定が存在しない場合だけ。元の個人向け初期設定は既存復元機能で読める非公開JSONへ分離した。
